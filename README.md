# asn1-codegen

The ASN.1-to-Rust compiler and PER (APER/UPER) codecs used by
[nextgcore](https://github.com/NextgCoreLab/nextgcore) (5G/EPC core network)
and [nextgsim](https://github.com/NextgCoreLab/nextgsim) (gNB/eNB/UE simulator)
to generate their 3GPP protocol codecs from the specifications' ASN.1.

It is a fork of [hampi](https://github.com/gabhijit/hampi) 0.7.2 -- the
`asn1-compiler`, `asn1-codecs` and `asn1_codecs_derive` crates -- carrying
conformance fixes found while generating NGAP, S1AP, NRPPa, LPP, NR RRC and
LTE RRC. It used to live in `nextgsim/vendor/`, which made the core network
depend on the simulator's repository to build; it is a standalone repository
so both products depend on a neutral library instead.

## Crates

| Crate | Role |
|---|---|
| `asn1-compiler` | Parses ASN.1 modules, resolves them, generates Rust types with PER derives (used from a consumer's `build.rs`) |
| `asn1-codecs` | The APER/UPER runtime the generated code calls |
| `asn1_codecs_derive` | The `#[derive(AperCodec, UperCodec)]` proc-macros |

Crate names **and** version (`0.7.2`) are unchanged from hampi, so a consumer
switches by changing only the dependency source:

```toml
[workspace.dependencies]
asn1-compiler      = { git = "https://github.com/NextgCoreLab/asn1-codegen", tag = "v0.1.0" }
asn1-codecs        = { git = "https://github.com/NextgCoreLab/asn1-codegen", tag = "v0.1.0" }
asn1_codecs_derive = { git = "https://github.com/NextgCoreLab/asn1-codegen", tag = "v0.1.0" }

# asn1_codecs_derive depends on the registry `asn1-codecs = "=0.7.2"`; route it
# here too, or the build links two different asn1-codecs.
[patch.crates-io]
asn1-codecs        = { git = "https://github.com/NextgCoreLab/asn1-codegen", tag = "v0.1.0" }
asn1_codecs_derive = { git = "https://github.com/NextgCoreLab/asn1-codegen", tag = "v0.1.0" }
asn1-compiler      = { git = "https://github.com/NextgCoreLab/asn1-codegen", tag = "v0.1.0" }
```

Generated code that uses the derives needs a direct `log` dependency (the
derive expands to `log::` calls).

## What is fixed relative to hampi 0.7.2

| Fix | Standard | Origin |
|---|---|---|
| CHOICE extension arm is encoded, not only decoded | X.691 §23 | nextgsim #117, PR #181 |
| Class fields written inline as a base type (`OCTET STRING (CONTAINING …)`) are kept in the open-type enum -- 14 NGAP MBS IEs, incl. mandatory IE 304, were silently dropped | X.681 information object classes; TS 38.413 | nextgsim #185, PR #187 |
| An object-set parse pass that consumes nothing is an error instead of an infinite loop | — (parser robustness) | nextgsim #45, PR #195 |
| Opt-in skipping of unknown IEs, surfaced with their criticality | TS 38.413 / 36.413 §10.3.4 | nextgsim #214, PR #217 |
| SEQUENCE OF SIZE enforced on encode; extensible SIZE encoded | X.691 §20.4 | nextgsim #212, PR #215 |
| ENUMERATED extension additions encode, and decode to the right value | X.691 §14 | nextgsim #213, PR #216 |
| An entry of an empty extension object set is a real open-type entry (was decoded as zero bits, misparsing the rest of the PDU) | X.691 §19, X.681 | nextgsim #218, PR #219 |
| Lengths ≥ 16K are fragmented on encode and reassembled on decode (decode previously corrupted fragmented open types silently) | X.691 §11.9.3.8 | nextgsim #222, PR #223 |
| Variable-size BIT/OCTET STRING content is octet-aligned at any length | X.691 §16.11, §17.8 | nextgsim #226, PR #227 |
| Extensible INTEGER values past the root encode; generated types are sized from the extension range | X.691 §12.1 | nextgsim #231, PR #235 |
| A constraint mixing single values and ranges takes the largest upper bound | X.680 constraint union | nextgsim #241, PR #242 |
| Character strings aligned by the type's upper bound; UTF8String size is not PER-visible | X.691 §30.5.7 | nextgsim #246, PR #247 |
| SEQUENCE extension additions and `[[ ]]` addition groups are generated and coded (Rel-15+ fields were dropped: NR RRC 2,561, LTE RRC 872, LPP 322 groups); normally-small length long form above 64 | X.691 §19.7–19.9, §11.6 | nextgsim #253, PR #256 |

Each fix is verified in its origin PR against octets derived by hand from
X.691, not only by round-trip.

## Generated-code guard

`codegen-golden` regenerates every schema the consumers compile, with their
`build.rs` settings (`Visibility::Public`, derives `Debug, Clone, PartialEq`,
APER for NGAP/S1AP/NRPPa, UPER for RRC/LPP), and compares a SHA-256 of each
**unformatted** output with `codegen-golden/golden/SHA256SUMS`. Any compiler
change that alters a generated byte fails CI until the golden file is updated
deliberately:

```sh
UPDATE_GOLDEN=1 cargo test -p codegen-golden --release
```

Pinned schemas (`codegen-golden/schemas/`): NGAP 17.9, S1AP 19.2.0, NRPPa
19.2.0 (nextgsim's and nextgcore's extractions), LPP 19.3.0, NR RRC 19.3.0,
LTE RRC 19.4.0.

## History

The three crates were extracted from nextgsim with their full history:
`git filter-branch --index-filter` keeping only `vendor/asn1-compiler`,
`vendor/asn1-codecs` and `vendor/asn1_codecs_derive`, moved to the repository
root, with `--prune-empty` (13 commits, the first being the vendoring of hampi
0.7.2 in nextgsim PR #181). PR numbers in commit subjects refer to nextgsim.

## Development

```sh
cargo fmt --all -- --check
cargo clippy --workspace --all-targets
cargo test --workspace --release
```

The forked crates carry hampi's existing clippy warnings; CI reports them but
denies warnings only in `codegen-golden`. Fixes should keep generated output
unchanged unless the change is the point -- in which case update the golden
hashes in the same PR and explain the diff.
